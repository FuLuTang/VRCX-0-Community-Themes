# 样式收敛方法

主题包只适配软件现有 DOM。不改软件，不加属性，不部署，除非用户另说。`[]` 可用，但只能匹配组件已经输出的 `data-slot`、`data-variant`、`data-size`、`aria-*`。函数名、未输出的 variant、为了命中新造的属性，都不能当选择器。

## 流程

1. 看看 ./和用户商讨后收敛的"每个组件什么样".md，有哪个组件还没做。一共是62种，从42个页面快找找出来的（用源码确认是不是同一组件、看DOM 上实际有什么。外观像，不等于组件相同；页面不同，也不等于组件不同。）优先从复用最多的开始入手。注意，如果是“一套”的，在同一轮处理。
2. 让subagent提取出这个组件多少处在用，到底有几种样式在混用。通过读tsx源码分析是否本该市场一类（也就是样式合并），还是从语义解读确实能分成几类？用类似 design-specs/jirai-kei-theme/checks/build-preview_tabs(exemple).mjs 生成一个类似 design-specs/jirai-kei-theme/checks/preview_tabs(exemple).html 的页面，方便直接看到底有哪些效果。然后把调查结果和展示页面发给主对话。（工具：tools/slot-census.mjs 查分布和现有样式种类；演示内容写在 tsx 里，参考 checks/tabs-visual-preview.tsx，打包可用 tools/build-preview.mjs）
3. 主对话处理信息后，和用户抉择这个/些组件可以最终收敛成几种样式（先在对话中把效果展示网页发给用户，然后对用户提出选择问题）
4. 决定后，主对话在 build-preview_xxx.mjs / preview_xxx.html 中应用决定后的效果，然后跟用户交互再进行最终样式确定
5. 让sunagent在 design-specs/jirai-kei-theme/runtime 中，执行:1,像其他的“层”一样，对当前要处理的组件(们)写一个单独的 components/xxx.css（如 components/tabs.css）2，把旧的散落在各处的匹配对应组件的css清理掉。检查最终效果确实是所希望的。关于 components/xxx.css，如果是多种多层匹配的话，主对话最好提前给设计好“到底分成几个层级”。（工具：动手前 tools/rule-owners.mjs 找旧规则、tools/build-compare.mjs save 存改动前；components/xxx.css 在 runtime/parts.json 插一行接入；改完 build-compare diff，再 style-diff --expect 目标组件，组件外必须 0 差异）
6. 主对话二次验证最终效果（复跑 style-diff，看预览页；用户要求时 tools/deploy-win.mjs 上实机）。没问题之后记录在 design-specs/jirai-kei-theme/checks/和用户商讨后收敛的"每个组件什么样".md（别忘了先看已有的是怎么写的）

## 对于一个组件如果有多种样式，该如何入手

分出：
- **默认：** 认得出组件身份，就有基础皮肤。新页面复用该组件即命中，不登记页面名。
- **半套：** 只追加装饰，不复制框、按钮和状态。单独记录，不并进成品。
- **特例：** 先说明它为什么特殊：在哪个现有容器、有什么现有结构。然后替换默认皮肤。并列特例互不继承。
- 现有 DOM 无法可靠区分时，保留原样。布局 class 只是脆弱代理，要标明，不能假装成稳定语义。
- 默认层不用 `!important` 压特例。特例要能退出默认层；覆盖必须盖住背景、选中态、阴影和指示器。

## 关于记录
不超过 25 行。不解释，不贴选择器，不嵌图片。半套单独一条。

## 关于css层级（以及如何记录）（这里的1234层不是指最终真的需要4层，而只是在这里展示如果有中样式，改怎么分配第几层。也就是最终产出的css是可以互相覆盖的，就像Minecraft的mods一样）
层级一（组件默认）：于{现有身份条件}的{组件}，使用此样式：

<div></div>

层级二（附加修饰）：于{现有结构条件}的{组件部位}，额外使用这半套，不另起基础皮肤：

<div></div>

层级三（特例）：于{现有容器或结构}内的{组件}，替换默认为此样式：

<div></div>

层级四与层级三并列，不继承层级三。文档里的“层级”是判定层次，不必对应 CSS `@layer`。

注意，subagent使用6luna。除了普通的prompt，也给他设计好todo和goal。
